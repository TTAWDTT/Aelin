# Aelin 五工具抽象化方案（context_get / diary / profile / tracking / device）

日期：2026-02-25  
作者：Codex  
状态：方案评审稿（不含代码）

## 1. 背景与目标

当前 Aelin 的能力已经覆盖了聊天、RAG、记忆、追踪、桌宠与设备控制，但执行入口分散在多个路由和服务中。  
这会带来三个现实问题：

1. 模型侧调用路径不稳定：同一任务可能走不同接口，导致行为不一致。  
2. 可观测性不足：难以统一统计“模型到底做了什么动作”。  
3. 演进成本高：每加一个能力，都要改多处 prompt、路由和前端契约。

本方案目标是把能力收口为 5 个工具族：

1. `context_get`
2. `diary`
3. `profile`
4. `tracking`
5. `device`

核心原则：

1. 工具是“能力边界”，不是“接口镜像”。  
2. 每个工具统一使用 `op` 表达动作（读、写、更新、执行）。  
3. 工具返回高信号、低冗余数据，避免浪费上下文窗口。  
4. 所有写操作可审计、可幂等、可回放。

---

## 2. 总体架构设计

## 2.1 分层

1. LLM 决策层：决定“要做什么”。  
2. Tool 编排层：把“意图”映射为 `工具名 + op + 参数`。  
3. 领域服务层：调用现有 `AgentMemoryService / TrackingAutonomyService / OpenVikingBridge / DeviceCenter`。  
4. 存储层：SQLite + OpenViking 文件系统 + 桌宠插件 API。

## 2.2 执行契约（统一格式）

每次工具调用都遵循同一生命周期：

1. 参数校验（字段完整性、workspace、权限）。  
2. 执行动作（读/写/执行）。  
3. 结果标准化（`ok`、`data`、`warnings`、`error`）。  
4. 记录追踪（tool trace、耗时、输入摘要、输出摘要）。  
5. 可选触发副作用（例如 diary 汇总、tracking ack、device 动作建议）。

这会直接提升 `tool_trace` 的解释力，便于前端和调试链路统一展示。

---

## 3. 五个工具的详细设计

## 3.1 `context_get`

### 3.1.1 是为了做什么

`context_get` 是 Aelin 对话前的“统一上下文入口”。  
它负责一次性返回当前轮需要的核心状态，而不是让模型分散调用多个读取接口。

### 3.1.2 如何实现

数据来源聚合：

1. 记忆摘要与分层记忆：来自 `AgentMemoryService`。  
2. 跟踪态势摘要：来自 `tracking` 领域状态（目标数量、未读变更、风险项）。  
3. 日记最近片段索引：来自 OpenViking diary 索引（可选）。  
4. 设备快照摘要：来自 `device`（CPU、关键进程异常、当前模式）。

实现要点：

1. 统一轻量返回：默认只返回摘要和关键 ID，不回传大文本正文。  
2. 支持模式参数：`light`（默认）与 `full`（调试）。  
3. 增加短 TTL 缓存（例如 3-8 秒）降低高频轮询成本。  
4. 附带 `suggested_actions`：由规则层生成“下一步建议”，替代独立 todo。

### 3.1.3 有什么意义

1. 稳定模型输入，显著减少“同问不同答”。  
2. 让 Aelin 每轮有统一“世界状态”，便于后续工具选择。  
3. 把原先分散读取成本前置并标准化，降低时延和 token 消耗。

---

## 3.2 `diary`

### 3.2.1 是为了做什么

`diary` 专注“人可读日记系统”，不承担任务状态机。  
它是“记录与阅读”能力，不是“调度能力”。

### 3.2.2 如何实现

建议 `op` 语义：

1. `append`：写入单条聊天/观察记录（raw 层）。  
2. `list`：列出日记树或按天列表。  
3. `read`：读取单篇日记正文。  
4. `rollup_daily`：将某天 raw 聚合为 daily，删除或归档碎片记录。

实现要点：

1. 继续使用 OpenViking 目录结构，保持文件系统可追溯。  
2. 明确双层结构：`raw`（过程记录）+ `daily`（人读总结）。  
3. 写入时只做最低清洗，不做模板化强约束，保证“像真实日记”。  
4. `rollup_daily` 支持幂等（重复执行不重复聚合）。

### 3.2.3 有什么意义

1. 满足“给人看”的真实可读性诉求。  
2. 保持来源可追踪（每条日记可回溯聊天与来源证据）。  
3. 通过日汇总降低数据碎片，改善长期维护和浏览体验。

---

## 3.3 `profile`

### 3.3.1 是为了做什么

`profile` 是“固定注入层”，用于存放用户画像、偏好、长期 notes。  
这部分信息每轮稳定注入，不作为 RAG 召回结果来碰运气。

### 3.3.2 如何实现

建议 `op` 语义：

1. `get`：读取画像条目（可按 namespace 或 key 过滤）。  
2. `upsert`：新增或更新画像条目。  
3. `delete`：删除过期或错误条目。

实现要点：

1. 数据结构建议 key-value + 元数据（来源、置信度、更新时间）。  
2. 更新时支持“冲突策略”：覆盖、合并、保留旧值。  
3. 对高风险字段增加写入门槛（例如需要明确确认语义）。  
4. 输出时区分“stable profile”和“volatile notes”。

### 3.3.3 有什么意义

1. 显著降低人物设定漂移。  
2. 避免把高价值偏好信息埋在 RAG 文档海中。  
3. 形成可治理的“长期人格记忆层”，提升对话连续性。

---

## 3.4 `tracking`

### 3.4.1 是为了做什么

`tracking` 是 Aelin 的任务与信号调度核心。  
你去掉 `to_do` 后，所有“待办/任务生命周期”都由 tracking 承接。

### 3.4.2 如何实现

建议 `op` 语义：

1. `create`：创建跟踪目标（支持手动任务类型）。  
2. `list`：列出目标与状态。  
3. `update`：更新状态、频率、通知级别、标签等。  
4. `run_now`：立即执行一次抓取。  
5. `changes`：读取目标变更事件。  
6. `ack`：确认已读变更。

实现要点：

1. 手动任务统一用 `track_type=manual_task`，不再另建 todo 数据域。  
2. 统一状态机：`active / paused / done / muted / expired`。  
3. `changes` 返回需可用于前端“时间线 + 待处理提醒”。  
4. 所有写操作带审计信息（who/when/why）。

### 3.4.3 有什么意义

1. 消除任务系统重复建设（todo 与 tracking 双轨并存的问题）。  
2. 把“信息追踪”和“人工待办”统一到一个生命周期模型。  
3. 让 Aelin 的主动提醒、决策建议、日记记录来源一致。

---

## 3.5 `device`

### 3.5.1 是为了做什么

`device` 提供系统状态读取与系统动作执行能力。  
它是 Aelin 触达真实设备的执行桥梁。

### 3.5.2 如何实现

建议 `op` 语义：

1. `status`：读取设备概况（负载、模式、关键状态）。  
2. `processes`：读取进程列表与异常评分。  
3. `action`：执行单进程动作（终止/优先级调整等）。  
4. `mode_apply`：应用设备模式。  
5. `media_control`：控制媒体播放与音量（可对接桌宠音乐链路）。

实现要点：

1. 动作类 `op` 必须安全分级（只读/低风险/高风险）。  
2. 高风险动作需明确确认语义并记录审计。  
3. 输出要友好：优先返回可读名称，不暴露底层噪声字段。  
4. 与桌宠插件 API 联动时，保持“前端即时反馈 + 后台异步执行”。

### 3.5.3 有什么意义

1. 让 Aelin 从“建议型助手”升级为“可执行助手”。  
2. 把设备控制纳入统一工具轨迹，便于复盘和风控。  
3. 为专注联动情绪引擎提供实时设备信号输入。

---

## 4. 工具间协同关系

典型链路（无 todo 版本）：

1. `context_get` 获取当前态势。  
2. 若用户要查进展，调用 `tracking.list` + `tracking.changes`。  
3. 若用户要执行动作，调用 `device.*`。  
4. 对关键对话结论调用 `diary.append`。  
5. 对稳定偏好或长期信息调用 `profile.upsert`。  
6. 日终执行 `diary.rollup_daily`。

意义：  
五个工具构成闭环，不需要第六个 `to_do` 也能覆盖“看见问题 -> 做出动作 -> 留下记录”。

---

## 5. 可观测性与治理

## 5.1 可观测性

每次工具调用都应记录：

1. `tool`、`op`、耗时、成功/失败。  
2. 参数摘要（脱敏）。  
3. 返回摘要（条数、关键 ID、错误码）。  
4. 与 `AelinToolStep` 的映射关系。

## 5.2 治理与安全

1. `workspace` 强隔离，禁止跨工作区读写。  
2. 写操作幂等键（防止重试造成重复写入）。  
3. 高风险 device 动作要确认门槛。  
4. profile 关键字段设冲突规则与回滚策略。

---

## 6. 分阶段落地计划（不改业务语义）

## 阶段 1：工具壳层

目标：先统一调用入口，不改底层服务实现。

1. 建立 5 个工具族 + `op` 路由。  
2. 接入统一参数校验和结果包装。  
3. 保留现有路由，工具层先做“薄封装”。

## 阶段 2：读写归并

目标：把散落逻辑逐步收束到工具实现。

1. diary 写入/汇总全部走 `diary` 工具。  
2. profile 注入全部走 `profile.get`。  
3. tracking 任务管理替代 todo 语义。

## 阶段 3：执行闭环

目标：强化可执行能力与风控。

1. device 动作加入风险分级与确认。  
2. context_get 增加 `suggested_actions` 与解释字段。  
3. tool trace 与前端展示完全对齐。

---

## 7. 验收标准

功能验收：

1. 任意一个用户请求，工具选择能收敛到这 5 类之一。  
2. 无 `to_do` 工具时，任务类需求能通过 `tracking` 完成。  
3. diary 日终汇总与 raw 清理流程稳定可复现。  
4. profile 注入稳定，不依赖 RAG 召回命中。

质量验收：

1. 工具调用成功率 >= 99%（读操作）和 >= 97%（写操作）。  
2. 平均工具调用耗时在可接受范围（按现网基线评估）。  
3. tool trace 可完整回放关键链路。  
4. 高风险 device 动作零越权。

---

## 8. 结论

将 Aelin 工具层收敛为 `context_get / diary / profile / tracking / device` 是正确方向。  
它在复杂度、可维护性和执行能力之间取得了平衡，且与你当前“去掉 todo、保留任务闭环”的目标一致。

下一步建议是先做“工具壳层”落地，再逐步把现有分散逻辑并入，不做一次性大迁移。
