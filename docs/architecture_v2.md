## 2. 核心原则

### 2.1 一核统领
- **Computer Use 是唯一核心**，一切能力为其服务
- 记忆、Tracking、多端联动、形象引擎，皆为 Computer Use 的能力延伸

### 2.2 输入统一
- **Human Input**：用户主动发起（Chat 对话）
- **Cron**：系统定时触发（后台自动执行）
- 二者统一流入 **Agent Loop**，无需两套处理逻辑

### 2.3 工具分层
- **感知层（先看）**：`screen_get`、`device`、`browser_state`
  - 解决"现在什么情况？"
  - 为决策提供上下文
- **处理层（再做）**：`browser_use`、`bash`、`app_use`
  - 解决"怎么达成目标？"
  - 实际改变环境

### 2.4 Tracking 后台化
- **不作为独立系统保留**，而是作为 Computer Use 的"数据源"
- 后台默默采集，为 `cron` 触发提供变化感知
- 无繁琐 UI，不喧宾夺主

### 2.5 记忆轻量化
- **退化为 RAG**：常规数据库存储 + 向量检索
- 为 Computer Use 提供"历史上下文"，非独立功能
- 弃复杂记忆结构，简化为"上下文检索"

## 3. 关键转变

| 旧架构 | 新架构 |
|--------|--------|
| 多核心并列（Chat、Tracking、Memory、Agent） | **单一核心**（Computer Use） |
| Tracking 作为独立功能系统 | **Tracking 后台化**，作为 Computer Use 的数据源 |
| 复杂记忆系统（OpenViking 兼容） | **轻量 RAG**，为 Computer Use 提供上下文 |
| 工具混杂，职责不清 | **工具分层**（感知层 vs 处理层） |
| 用户面对多个界面（Chat、Desk、Tracking） | **统一入口**（Chat + 自动化触发） |

## 4. 实施路径

### Phase 1：核心重构（2-3 周）
- **目标**：建立 Computer Use 核心，验证单一任务自动化
- **行动**：
  1. 重构 `aelin_tools.py`，明确分层（感知/处理）
  2. 实现 `screen_get` + `browser_use` 最小闭环
  3. 选择 1 个用户高频重复任务，实现自动化
- **验收**：能自动完成一个真实任务，用户无需干预

### Phase 2：输入统一（1-2 周）
- **目标**：整合 Cron 触发，实现定时自动化
- **行动**：
  1. 将原 Tracking 数据接入 Computer Use 作为数据源
  2. 实现 Cron 定时触发 Agent Loop
  3. 支持"定时检查 → 发现变化 → 自动执行"流程
- **验收**：能定时自动检查并执行任务，无需用户发起

### Phase 3：记忆简化（1 周）
- **目标**：替代复杂记忆系统为 RAG
- **行动**：
  1. 设计轻量 RAG 存储（向量数据库 + 元数据）
  2. 迁移关键历史数据
  3. 为 Computer Use 提供上下文检索接口
- **验收**：Computer Use 能检索历史上下文，辅助决策

### Phase 4：验证与迭代（持续）
- **目标**：验证价值，持续优化
- **行动**：
  1. 自用 + 邀 3-5 位开发者试用
  2. 收集高频场景，扩充工具能力
  3. 优化稳定性、错误处理、用户体验
- **验收**：用户（包括君自己）每日使用，若停用则感不便

## 5. 结语

此架构之要，**一言以蔽之**：

> **Computer Use 为唯一核心，万法归宗。**
> **输入统一、工具分层、记忆简化、Tracking 后台化。**
> **由"多核心并列"进化为"单一核心+能力延伸"。**
