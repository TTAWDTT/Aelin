# Aelin PR18 自我代码审查

## 范围

本文件只审查我在 `codex/browser-login-recovery` 这条线上交付的代码，而不是泛泛而谈整个仓库。重点覆盖：

- 浏览器登录确认与续跑协议
- CDP / 受控浏览器恢复链路
- browser executor 的并发与超时处理
- 前端确认流和会话续跑交互
- merge `origin/main` 后与附件链路的耦合问题

结论先说：这批代码已经从“能演示”推进到“能工作”，但距离“长期可维护”还有明显差距。最大问题不是功能缺失，而是状态机、边界和责任分层仍然偏散。

## 1. 登录恢复协议仍然太隐式

我这轮把 `login_request_id`、`next_call`、`resume_request`、`resume_query`、`continue_after_confirm` 串起来了，功能上能跑，但协议设计并不干净。

具体问题：

- 确认接口同时承担了“确认浏览器动作”“恢复待续任务”“返回最终 follow-up 结果”三种职责。
- `continue_after_confirm` 的语义并不天然，必须结合 `continued`、`continuation_error`、`followup_result` 一起读，调用方理解成本高。
- `requires_followup` 是事后补正的字段，说明最初协议没有把“是否还欠一次续跑”建模清楚。
- 服务端状态和前端状态都能影响续跑行为，容易形成“谁是真相源”的歧义。

风险：

- 以后如果再引入更多 checkpoint 类型，比如验证码、文件选择器、2FA、系统权限弹窗，这套协议会继续膨胀。
- 现在的字段组合更像是一次次补丁叠上去，而不是显式状态机。

我认为更合理的方向是：把浏览器 checkpoint 统一收敛成显式状态模型，例如 `pending -> confirmed -> resumed -> completed / failed`，而不是让多个布尔字段拼语义。

## 2. 路由层业务过重

`backend/app/routers/aelin_chat.py` 现在已经不只是路由层：

- 有 SSE 流转发
- 有浏览器确认执行
- 有登录状态恢复
- 有附件上传入口
- 有错误规约与日志记录

这会导致两个后果：

- merge 冲突非常频繁。这次和 `origin/main` 冲突最重的就是这个文件，已经证明它是热点耦合点。
- 测试虽然能覆盖分支，但代码演化会越来越痛，因为每次改动都容易碰到跨领域逻辑。

问题不在于“代码长”，而在于它已经成为多个子系统的交汇层。我这次虽然把冲突解掉了，但本质上是在继续容忍这个热点文件变得更胖。

建议：

- 把浏览器确认/恢复逻辑抽到独立 service。
- 把 SSE 事件拼装和路由层解耦。
- 把附件上传相关逻辑完全从 chat router 拆出去。

## 3. executor 改善了超时语义，但资源模型仍粗糙

我修了 `browser_exec` 的两个关键点：

- 增加 inflight semaphore，防止堆过多同步 Playwright 任务。
- 超时后不立刻释放 slot，而是等真实任务完成再释放，避免假空闲。

这是必要修复，但它还不是一个完整的资源调度模型。

问题：

- 当前 semaphore 是全局级别的，隔离粒度不够。一个用户的慢任务可能拖住其他用户。
- `browser_tool_busy` 是一种硬拒绝，没有排队、优先级、租约可视化，也没有观测层告诉我们“为什么忙”。
- 我补了测试保证线程池能 `finally` 清理，但这只是测试卫生，不是生产资源治理。

换句话说，我解决的是“明显错误”，还没有解决“可运营”。

## 4. 前端 send 流程还是太中心化

`frontend/src/features/chat/hooks/useChatStream.ts` 现在把这些职责都放在一个 hook 里：

- 创建会话
- 写入用户消息
- 创建 assistant 占位消息
- 处理图片输入
- 处理附件输入
- 处理 SSE 流
- 处理中断
- 处理 tool trace 聚合

我这次 merge 时把图片流、附件流、中断恢复一起并进来了，功能上没丢，但结构上还是中心化。

问题：

- `send` 已经是高耦合入口，继续叠需求会越来越难读。
- 中断逻辑依赖 `abortRef.current === cancel` 这种约定式比较，实用但并不优雅。
- tool trace 的查找依赖 session 内最后一条 assistant message，默认 UI 状态总是整洁；这类假设一旦被未来特性打破，会很难排查。

我认为这里至少应再拆两层：

- 纯请求构造层
- 纯流事件归并层

否则继续演化时，这个 hook 会成为前端版的 `aelin_chat.py`。

## 5. resume_request 处理仍有历史包袱

我已经把 confirm payload 里的大图 `data_url` 去掉，改成服务端保存 resume context + 前端只传 `login_request_id` / `next_call`。这是正确方向。

但问题没有完全结束：

- 服务端当前仍然要同时兼容“新式 resume 协议”和“payload 直接带 resume_request 的旧路径”。
- 这意味着协议迁移尚未彻底完成。
- 一旦某些客户端版本落后，后端会继续背兼容负担。

这类兼容期如果拖太久，最后会变成永久双轨。我的代码目前还没给出明确淘汰路径。

## 6. 真实浏览器场景仍受底层技术栈限制

这轮实现的目标不是“彻底绕开登录限制”，而是：

- 拉起受控浏览器 / CDP
- 在需要人工登录时进入 checkpoint
- 用户完成登录后继续恢复执行

这个方案现实可用，但也必须诚实承认边界：

- 如果 Playwright Sync / Async 混用、CDP endpoint 异常、Chrome 进程残留，恢复链路仍然会失败。
- 如果目标站点用强反自动化策略，我们仍然会碰到页面不可稳定操作的问题。
- 当前方案并没有实现真正意义上的“无人值守自动登录”，只是把“人工介入点”建模成可恢复状态。

也就是说，这轮代码解决的是“登录后如何继续”，不是“如何无凭据自动过所有登录墙”。这一点如果在产品叙事上说不清楚，后续很容易被误解成能力已经闭环。

## 7. merge 兼容性靠人工判断较多，自动守护不够

这次把 `origin/main` 的附件能力合进来后，我手工合并了：

- chat router 导入与附件上传入口
- core 里的 attachment_ids / llm fallback
- message builder 里的 attachment_search 预取上下文
- 前端 send 对 attachment_ids 的支持
- test_aelin_tools 里两边新增的测试

这次能合住，是因为我理解了两边的意图。但这恰好暴露了另一个问题：

- 我们对这些关键拼接点缺少更高层的集成测试。
- 如果下一次 main 再改消息构造、再改 router、再改前端流协议，冲突仍会高发。

现在的自动化测试更多是“函数级正确”，还不够保证“跨层协议不漂移”。

## 8. 测试覆盖比之前好，但还没覆盖真正复杂的失败态

我这次补了：

- `requires_followup` 在不同续跑分支下的测试
- executor 清理安全性的测试
- merge 后已有浏览器/附件相关测试的兼容

但依然没完全覆盖这些场景：

- 浏览器确认成功、续跑请求构造成功、下游 LLM 超时或返回结构异常。
- login state 已过期，但前端仍试图继续确认。
- attachment 与 screenshot 同时存在时，消息构造优先级是否符合预期。
- 多个登录 checkpoint 并存时，前端和后端如何避免串单。

所以这批代码目前是“关键路径可测”，但离“失败路径充足可测”还有距离。

## 9. 文档和代码抽象还不同步

我已经在代码里体现了 openclaw 风格的“受控浏览器 + checkpoint + resume”思路，但仓库里的抽象名词还不完全统一：

- 有时叫 login checkpoint
- 有时叫 confirm flow
- 有时叫 browser confirm
- 有时又落到 resume_request / next_call 这种低层协议字段

这会让新同学理解系统时先看到实现细节，而不是先看到模型。

理想状态应该是：

- 文档先定义对象模型
- 代码再映射到字段
- 前后端共享同一套术语

现在还没做到。

## 10. 我对自己的总体评价

如果只问“这批代码值不值得合进主线”，我的答案是：值得，但附带技术债说明。

理由：

- 它确实解决了一个真实而关键的产品痛点：人工登录后续跑。
- 它把原本一次性失败的链路，改成了可恢复、可确认、可继续。
- 它在安全性上比“偷偷重放原 payload”更稳健。

但如果问“这是不是一套优雅、长期低成本的设计”，我的答案是否定的。

真实评价是：

- 这是一次正确方向上的工程推进。
- 也是一次带着明显耦合和协议债前进的推进。
- 我修掉了明显 bug，也把功能做通了，但没有假装所有结构问题都已经解决。

## 后续最该做的三件事

1. 把浏览器 checkpoint / resume 协议收敛成显式状态机和单一 DTO。
2. 把 `aelin_chat.py` 从“总线型热点文件”拆成更小的路由与服务边界。
3. 增加跨层集成测试，覆盖 login checkpoint + attachment + stream 三者并存的真实链路。

如果这三件事不做，PR18 能 merge，但后续维护成本会持续上升。
