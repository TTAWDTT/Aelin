# Goose Dev plane 接入任务清单（TODO + 验收标准）

> 目标：按照「plane + tool」架构，将 goose 集成为负责工程/开发任务的 Dev plane。  
> 本文只列待办项和验收标准，不包含实现细节。

---

## 阶段一：设计与准备

- [ ] 1.1 确认 goose Dev plane 的能力边界
  - [ ] 验收：`docs/goose_plane.md` 中「适合交给 goose / 不该交给 goose」的例子覆盖常见场景（修 bug、加接口、补测试、重构、小工具开发）。
  - [ ] 验收：明确写出哪些任务必须交给 pinchtab / gws / 其它 plane，而不是 goose。

- [ ] 1.2 选定与 goose 的集成方式（CLI / 本地 server）
  - [ ] 验收：列出候选接入方式（至少 CLI 方案 + 如有则 server 方案），比较优缺点。
  - [ ] 验收：在文档中明确当前阶段采用的唯一方式（例如：先用 CLI），并说明原因。

- [ ] 1.3 规划 goose 的工作目录与权限范围
  - [ ] 验收：定义「允许 goose 操作的项目目录白名单」策略（例如：当前 workspace 仓库目录）。
  - [ ] 验收：在文档中写清楚 goose 不得访问的路径类型（系统盘根目录、用户隐私目录等）。

## 阶段二：后端 Dev plane 抽象与最小接入

- [ ] 2.1 定义 Dev plane 抽象接口
  - [ ] 验收：在 backend 中新增统一的 Dev plane 抽象（例如 Python 协议/类），至少包含：
    - [ ] `start_dev_task(task_spec) -> task_id`
    - [ ] `get_task_status(task_id) -> { status, steps[], logs?, partial_results? }`
    - [ ] `cancel_dev_task(task_id) -> ack`
  - [ ] 验收：接口文档中说明 `task_spec` 必须包含：任务自然语言描述、工作目录、允许改动范围、风险级别、资源上限。

- [ ] 2.2 实现 goose 版 Dev plane 适配器（MVP）
  - [ ] 验收：实现一个最小版的 goose 适配器，只支持在单一本地仓库目录内运行简单任务（例如「在 README 里追加一段文字」）。
  - [ ] 验收：`start_dev_task` 能成功调用 goose（通过选定的 CLI / server 方式）并返回一个可追踪的 `task_id`。
  - [ ] 验收：`get_task_status` 能够返回：
    - [ ] 合理的 `status`（running/completed/failed）。
    - [ ] 至少 3 条以上的 `steps[]`（例如：分析 → 编辑文件 → 运行命令）。
  - [ ] 验收：`cancel_dev_task` 调用后，新的轮询结果会反映任务已终止或不再继续推进。

- [ ] 2.3 添加基础日志与错误处理
  - [ ] 验收：遇到 goose 启动失败、路径无效、权限不足等情况时，返回清晰的错误信息给 Aelin，而不是静默失败或仅有堆栈。
  - [ ] 验收：所有 goose 相关日志都有统一的 log 前缀（例如 `goose_plane`），便于排查。

## 阶段三：与 agent loop 的集成

- [ ] 3.1 在 agent loop 中接入 goose Dev plane 作为可选执行路径
  - [ ] 验收：当用户提出工程类需求时，Aelin 能在内部推理中考虑「委派给 goose Dev plane」这一选项。
  - [ ] 验收：在不改动现有 pinchtab / gws 行为的前提下，将 goose plane 纳入统一的 plane 选择逻辑。

- [ ] 3.2 规范化 task_spec 的构造流程
  - [ ] 验收：在 agent loop 中，Aelin 会在调用 goose 前明确整理：
    - [ ] 用户需求文本；
    - [ ] 当前工作目录（或项目标识）；
    - [ ] 允许改动路径列表；
    - [ ] 风险等级（谨慎/正常/激进）；
    - [ ] 时间/步骤预算。
  - [ ] 验收：对于信息不足的情况，Aelin 会先向用户进行补充提问，而不会构造含糊的 task_spec。

- [ ] 3.3 将 goose 的步骤与状态对接到统一 trace 结构
  - [ ] 验收：agent loop 在获得 `steps[]` 后，能够将其映射到统一的 plane trace 结构中（与 pinchtab 设计一致或兼容）。
  - [ ] 验收：goose 每一步的描述尽量简洁中文/英文自然语言，而不是原始日志堆栈。

## 阶段四：前端 UI & plane trace 呈现

> 说明：本阶段所有前端工作**依赖 pinchtab plane 的前端链路与 plane trace UI 先落地**。  
> 当前阶段只作为规划与占位，不立即实装，等 pinchtab 的 plane UI 稳定后，统一复用到 goose。

- [ ] 4.1 在 chat 时间线中展示 goose plane 任务 chip
  - [ ] 验收：当 Aelin 决定委派任务给 goose 时，会在 chat 中插入一条清晰的提示卡片，例如：
    - [ ] 「已委派给 goose Dev plane：xxx」；
    - [ ] 显示当前状态（等待中/进行中/完成/失败）。
  - [ ] 验收：任务 chip 与 pinchtab 等其它 plane 的展示形式保持风格一致（同一设计语言）。

- [ ] 4.2 在右侧 trace 面板中增加 goose 链路视图
  - [ ] 验收：在 plane trace 面板中可以选择查看 goose 相关链路：
    - [ ] 列出该任务的步骤列表 `steps[]`；
    - [ ] 支持展开查看关键日志片段。
  - [ ] 验收：当 goose 任务完成时，trace 默认折叠为简要摘要，用户需要时可以展开。

- [ ] 4.3 添加任务取消与重试的前端入口
  - [ ] 验收：在 UI 上为 goose plane 任务提供「取消任务」按钮，点击后会调用后端的 `cancel_dev_task`。
  - [ ] 验收：对失败的任务提供「基于当前上下文重试」按钮，点击后会让 Aelin 构造新的 task_spec 再次调用 goose。

## 阶段五：安全控制与资源约束

- [ ] 5.1 落实目录白名单与危险操作限制
  - [ ] 验收：后端在构造 goose 任务前，会检查工作目录是否在允许范围内，否则直接拒绝并给出提示。
  - [ ] 验收：对于明显危险的命令或改动类型（如删除大量文件、修改系统配置），在设计上有防御机制（例如不向 goose 暴露这些能力，或在 Aelin 侧进行额外确认）。

- [ ] 5.2 设置任务时间与步骤上限
  - [ ] 验收：每个 goose 任务都有合理的最大执行时间与最大步骤数，超出后 Aelin 会主动终止任务并告知用户。
  - [ ] 验收：在日志或 trace 中能清晰看到因超时/超步数导致的终止原因。

- [ ] 5.3 基础回滚/保护策略（中长期）
  - [ ] 验收：在有 git 仓库时，执行 goose 任务前有基础保护措施（例如提示用户自行 commit 或在文档中明确建议）。
  - [ ] 验收：文档中说明如何在 goose 任务结果不满意时回滚变更（手动 git reset / 切分支等）。
